Tokenised size comparison

A fourteen-line program run through each machine's tokenizer (same program, not translated). About 68% between the lightest and heaviest machine and dialect.

Sinclair has a 5-byte binary form stored after every numeric literal; the CPC has additional line overhead. ZX80's 141 has no floating point to encode which saves space. This is why a program fit check can't simply reuse the source machines byte count, it has to re-tokenize for each target.

Memory maps

Arranged by documented address region. Again this can be generalised, some machines have more complex memory layouts. CPC uses a non-linear line stepping structure for screen memory for example.

The Sinclair layouts have no screen region — the display file lives inside program RAM and moves as the program grows.

Silent breakages

Risky constructs that don't break but can lead to unexpected behavior when porting between dialects.

Correlation between diff cost and structural risk count is 0.58. 36 of the 182 pairs carry no structural risk at all; 20 carry 4 or more. The 5 worst all target the ZX80, which the matrix scores as low as 46.

Variable collisions

When a variable name is reused across different machines, it can lead to unexpected behavior.

69 pairs collide plain names, another 27 collide only marked ones — the class my earlier reading missed entirely. The Atom and ZX80 use single-letter for everything.
