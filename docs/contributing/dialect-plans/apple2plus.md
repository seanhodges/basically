# Apple II Plus dialect — implementation plan

> Generated by the `adding-a-target-system` skill on 2026-08-30. Each stage is a
> medium, single-session task for the coding agent. Run them in order; the
> scaffolding under `src/dialects/apple2plus/` is throwing stubs until filled in.
> The dialect is **not** registered until the last stage, because registering it
> turns on the registry-driven batteries all at once — the memory map, the run
> measurements and the whole reference-docs set among them.

**Read `apple2.md` first, and finish it first.** This is the sibling of that
plan's machine: the same hardware with Applesoft in ROM instead of Integer
BASIC. It is _not_ a delegation sibling in the `bbcmaster` / `atari400` sense —
those import a sibling's whole language layer because they run the same BASIC,
and these two do not run the same BASIC at all. What is inherited here is the
machine: the emulator, the charset and the keyboard. What is written fresh is a
complete Microsoft-family language layer and a second set of samples.

## Target summary

- **id / name:** `apple2plus` / `Apple II Plus`
- **CPU / bus pattern:** none of its own — `src/emulator/apple2/`, built by
  `apple2.md`, configured with an Applesoft `Apple2BasicSupport` object (see
  _Pair split_ in that plan). No new emulator, no new npm dependency.
- **Display size:** `{ width: 280, height: 192 }`, as the sibling.
- **Image / tape format:** the machine's cassette records, written by Applesoft's
  `SAVE` and read by `LOAD`. The modulation is the same as the sibling's; the
  record framing is Applesoft's own (see Stage 4).
- **ROM:** `public/roms/apple2plus.rom` — 12288 bytes covering `$D000`–`$FFFF`:
  Applesoft II at `$D000`–`$F7FF` and the Autostart Monitor at `$F800`–`$FFFF`.
  This is the file usually distributed as `APPLE2.ROM`. Apple Computer copyright,
  and Applesoft is additionally Microsoft's work under licence — shipped on the
  same de-facto tolerance as the other bundled ROMs, and recorded in
  `public/roms/ATTRIBUTION.md` under the existing `# Apple ROM attribution`
  heading. **The Microsoft half is worth naming explicitly in that block**: the
  Apple I's entry can say "both are Wozniak's code", and this one cannot.
- **Share verb:** `hgr` — `HGR`, Applesoft's hi-res command and a keyword the
  sibling's Integer BASIC does not have. Unique in `src/player/routes.ts`
  `SHARE_VERBS`.
- **Reuse:** `src/emulator/apple2/` and `src/dialects/apple2/`'s `charset.ts` and
  `keyboardLayout.ts` (imported member by member, the way `atari400/index.ts`
  imports `atari800`'s — never spread over the sibling, so what is inherited and
  what is owned is visible in one file); `src/emulator/microsoftBasicLoad.ts`;
  `src/editor/variableLint.ts`'s Microsoft-family helper;
  `src/dialects/sampleKit.ts`; `src/dialects/targetHelpers.ts`.
- **License note:** none beyond the ROM.

## Why the language layer cannot be shared

Applesoft II is Microsoft 6502 BASIC — the same interpreter family as the C64's,
the PET's, the VIC-20's, the TRS-80's Level II, the Altair's 8K and the PMD 85's
BASIC-G, all of which already ship here. That is the family whose plumbing the
repo already has:

- **One-byte tokens with the high bit set** (`$80`–`$EA`), a flat table rather
  than the sibling's position-dependent syntax-table ordinals. A scanner, not a
  parser.
- **A linked-list program at `$0801`** — two-byte link, two-byte line number,
  tokenized text, `$00` terminator, and a zero link ending the program.
- **The standard zero-page workspace**: `TXTTAB` `$67`, `VARTAB` `$69`,
  `ARYTAB` `$6B`, `STREND` `$6D`, `FRETOP` `$6F`, `MEMSIZ` `$73`, `CURLIN` `$75`.
  Verify each against the ROM; they are the addresses `microsoftBasicLoad.ts`
  wants as its `programBase` and `pointers`.
- **Floating point, real strings, `DEF FN`, `ONERR GOTO`, `GET`** — none of which
  the sibling has, and all of which change what the samples can be.

So Stage 1 here is a genuine language core, not an import list. What it _is_ is a
well-trodden one: read `src/dialects/commodore64/tokenizer.ts` and
`src/dialects/trs80/` before starting, and expect the shape to fall out of the
family rather than out of this machine.

## Stage 1 — Language core ⬜

Text ↔ tokenized program bytes; no registry change.

- [ ] `addresses.ts` — the zero-page workspace words above, the ROM window and
      its two halves, `$0801`, and the display bases the dialect's own code
      needs. Read off the image, not from memory
- [ ] `keywords.ts` — `KeywordInfo[]` for the `$80`–`$EA` table, in the ROM's own
      order, with `kind`, signature and doc for each. Confirmed by typing each
      keyword at the `]` prompt and reading the stored byte back
- [ ] `charset.ts` — **import the sibling's.** The 2513 font and the
      normal/flash/inverse encoding are the machine's, not the BASIC's. Re-export
      rather than re-derive, so the two cannot drift
- [ ] `language.ts` — `languageSupport()` + `completionSource`. `$` and `%` are
      both suffix chars here (there is a second numeric type to tell apart,
      unlike on the sibling); no hex literal; `crunched` per what the ROM
      actually does with spaces
- [ ] `APPLE2PLUS_CONSTRUCTS` in `src/editor/constructs.ts` — Applesoft has
      `ONERR GOTO`, `DEF FN` and `GET` that the sibling's list does not, so this
      is its own array rather than a reuse of `APPLE2_CONSTRUCTS`
- [ ] `apple2plusVariableErrors` in `src/editor/variableLint.ts` over the
      Microsoft-family helper — Applesoft takes long names but is significant in
      only the first two characters, and a name containing a keyword is a syntax
      error, which is exactly what that helper exists to catch
- [ ] `tokenizer.ts` / `detokenizer.ts` — collect `TokenizeError[]`, never throw;
      `detokenizeWithReport` for import-fidelity warnings
- [ ] `basicImage.ts` — tokenized bytes → the loadable image and back, plus the
      `basicImagePointers()` that `microsoftBasicLoad.ts` takes as its `pointers`
- [ ] `lint` wired through `tokenize`
- [ ] tests: tokenizer round-trip over every keyword, link-field consistency
      after a re-tokenize, image-builder pointer consistency

**Depends on:** the `Dialect` contract, and `apple2/charset.ts`.
**Verify:** `npm test` + `npm run typecheck`.

the one `apple2.md` built.

- [ ] `public/roms/apple2plus.rom` **+ an attribution block in

- [ ] the Applesoft `Apple2BasicSupport` object — `loadProgram` (through
      `microsoftBasicLoad.ts`: write the image at `TXTTAB`, fix the workspace

      program), `currentLine` off `CURLIN`, and the three read-backs Stage 5
      fills in
- [ ] `createEmulator` on the dialect, handing `Apple2Machine` this ROM and this
      support object
- [ ] `debuggable: true` — `CURLIN` names the executing line
- [ ] tests: boot this ROM to the `]` prompt, inject a program, `RUN` it and read
      the screen back; a re-`LIST` after injection matching the source

**Depends on:** Stage 1, and `apple2.md`'s Stage 2.
**Verify:** the boot test passes.

## Stage 3 — Wire-up: keyboard + samples ⬜

No registry change here. Verify by booting the real ROM through
`src/dialects/bootHarness.ts` and reading `readScreenText()` back.

- [ ] `keyboardLayout.ts` — **import the sibling's**, with this dialect's own
      `id`/`name`/`theme`. It names `vk-theme-apple2plus`; the stylesheet block
      waits for Stage 7. No `graphicsPalette`, and not in `e2e/paletteMachines.ts`
- [ ] `samples/` + `samples.ts` via `standardSamples` — all five canonical
      programs, written for Applesoft. They are **not** ports of the sibling's:
      floating point, `HGR`/`HCOLOR=`/`HPLOT` and real string functions make
      these different programs, and `circles` and `kaleido` in particular should
      use hi-res where the sibling uses lo-res, because that is what this machine
      is remembered for. `breakout` keeps the same `PEEK(-16384)` /
      `POKE -16368,0` keyboard idiom — `GET` blocks, so it is not the answer for
      a real-time loop
- [ ] `memoryBlocks.ts` — `MemoryBlocksSupport` for `kaleido.bas`'s routine.
      `$0300` again, but **check it against this interpreter's own use of page 3**
      before committing: Applesoft and the Autostart Monitor between them claim
      more of the low pages than Integer BASIC does, and the hi-res pages at
      `$2000`–`$5FFF` are RAM the sibling's lo-res samples never touched. Stage 5
      rechecks the figures against the map
- [ ] every sample **run on the machine** and fixed until its screen is right
      (`authoring-dialect-samples`)
- [ ] finalize `aiProfile.ts` — and make it earn its place next to the sibling's.
      The traps worth teaching are the ones that catch someone who knows the
      other Apple II BASIC: `RND(1)` returns a fraction here and an integer
      there, `HIMEM:` moves a different pointer, and Applesoft is markedly slower
      at integer arithmetic than Integer BASIC despite the name
- [ ] `index.ts` — assemble the full `Dialect`, importing the sibling's charset,
      keyboard and machine member by member (placeholder picker identity until
      Stage 7)
- [ ] tests: keyboard matrix, samples tokenize cleanly **and run**

**Depends on:** Stages 1–2.
**Verify:** `npm run typecheck` + `npm test`.

## Stage 5 — Memory map & runtime introspection ⬜

- [ ] `memoryMap.ts` — the same hardware regions as the sibling's, with this
      machine's ROM window and zero-page workspace. Write it, do not import it:
      the interpreter half genuinely differs, and a shared map would have to lie
      about one of the two machines
- [ ] re-check `memoryBlocks.ts` against the map — `memoryMapDetail.test.ts` pins
      the program region to `memoryBlocks.programArea`
- [ ] `vars.ts` → `readVariables()`. The Microsoft variable table between
      `VARTAB` and `ARYTAB`, then the arrays to `STREND`, with strings living
      down from `FRETOP` — `src/dialects/commodore64` and `src/dialects/trs80`
      have both halves of this already
- [ ] `reports.ts` → `readReport()`. `?SYNTAX ERROR`, `?OUT OF DATA ERROR`,
      `?TYPE MISMATCH ERROR`, `?OUT OF MEMORY ERROR`, `BREAK IN <line>` — read
      off the screen and confirmed by provoking each
- [ ] `readMemoryStats()` — **every pool**: the program, the variables, the
      arrays, and the string space growing down from `MEMSIZ`. String churn is
      most of what a BASIC program does with memory, and a figure that counts
      only the program area moves for none of it
- [ ] memory-activity hooks for the memory-map overlay
- [ ] tests: memory-map layout, block round-trip, a live variable read back

**Depends on:** Stages 2–3.
**Verify:** memory-map + blocks tests; the watcher shows live vars.
