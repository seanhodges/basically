# Glyph sources

Every charset mapping in this project asserts "machine code `N` looks like
unicode character `X`". This page records the other half of that claim: **where
the shape came from on the real machine**, so a mapping can be traced back to its
evidence, and so a shape can be found by the address it lives at.

The address here is the address the **machine** sees, not the unicode code point
(that is the identifier of the IDE's bundled font, which is a different thing)
and not the offset in the ROM image this repo happens to ship. Those genuinely
differ — the Spectrum 128's font sits at offset `0x7D00` of the 32K dual-ROM
image but at `0x3D00` on the machine, once that bank is paged in — so both are
recorded.

The declarations live in `src/dialects/glyphSources.ts`; the tables below are
generated from them by `scripts/gen-glyph-addresses.mts` (`npm run gen:glyphs`),
and `glyph-sources.test.ts` regenerates and diffs, so they cannot drift from the
code. Do not hand-edit between the markers; everything outside them is
hand-written and preserved.

## Three kinds of source, because not every shape is stored

The tempting mistake is to assume every character has a bitmap at an address.
Most do not.

- **In a ROM we ship.** The Sinclairs, the Spectrums, the BBC's MODE 0–6 font,
  the Commodores and the CPCs keep their glyphs in an addressable ROM. These have
  a real machine address, and it is checkable: `glyph-sources.test.ts` reads each
  ROM at the declared offset and asserts a named anchor character renders as the
  shape it should.
- **Inside a video chip.** The BBC's MODE 7 alphanumerics are in the SAA5050, the
  Atom's in the MC6847, the TRS-80's in the MCM6670 — mask ROM the CPU cannot
  address at all. What is recorded is the chip's own index into that ROM, which
  is the only address those parts have.
- **Not stored at all.** Every machine's block graphics are generated
  combinationally from the bits of the character code — the SAA5050 builds a
  mosaic from bits 0–4 and 6, the MC6847 its semigraphics from the low six bits,
  the TRS-80's video logic likewise. There is no bitmap and no address, and
  inventing one would be a fiction. This is why "which address is that mosaic at"
  has no answer, and it covers precisely the semigraphics
  [the support matrix](./semigraphics-support) is about.

## Why the anchors are shapes and not checksums

A wrong base is invisible. Every offset into a ROM returns bytes, and most of
them look font-ish if you squint — the Master's font was first "found" at an
offset that turned out to be a sideways ROM bank, and only rendering the glyph
showed which reading was right. So each ROM-backed machine names one anchor
character and the exact bitmap it must draw. Every machine's `A` is visibly its
own: the ZX80's is wider than the ZX81's, the VIC-20 and PET have a pointed apex
the C64 has not, the CPC's is a row taller.

| BBC Master | 0x20-0x7F | SAA5050 internal ROM | 6×10 |
| BBC Master | 0xA0-0xBF, 0xE0-0xFF | generated by SAA5050 | 6×10 |
| C64 | 0x20-0x7F, 0xA0-0xFF | `c64/chargen.bin` @ 0xD000 | 8×8 |
| PET | 0x20-0x7F, 0xA0-0xFF | `pet/characters-2.901447-10.bin` (machine address not established) | 8×8 |
| VIC-20 | 0x20-0x7F, 0xA0-0xFF | `vic20/chargen.bin` (machine address not established) | 8×8 |
| Atom | 0x20-0x5F | MC6847 internal ROM | 8×12 |
| Atom | 0xA0-0xDF | generated by MC6847 SG6 | 8×12 |
| TRS-80 | 0x20-0x7F | MCM6670 internal ROM | 8×12 |
| TRS-80 | 0x80-0xBF | generated by video logic | 8×12 |
| CPC 464 | 0x00-0xFF | `cpc/cpc464.rom` @ 0x3800 | 8×8 |
| CPC 6128 | 0x00-0xFF | `cpc/cpc6128.rom` @ 0x3800 | 8×8 |

The address column is the address **on the real machine**. Where it reads
"generated", nothing is stored anywhere - the shape comes out of the code's
own bits - so there is no address to record and none is invented.

## Known wrinkles

### The BBC Master keeps its font outside the MOS

The Micro's font is the first thing in `os.rom`, at `0xC000`. The Master's
`mos3.20` is a 128K image — the MOS in its first 16K, then seven sideways banks —
and its MOS carries no font at all. The only font in the image is in the last
bank. The bank number follows from jsbeeb's own `loadOs` arithmetic rather than
from observing the machine, so the recorded address is derived, not measured;
the anchor assertion pins the bytes either way.

### The Commodore character ROM is indexed by screen code

The character generator knows nothing about PETSCII — the KERNAL converts on the
way to screen RAM, and the ROM is indexed by the result. `petsciiToScreen()` does
that conversion, and it is checked against the ROM itself rather than against a
table: PETSCII `0xC1` must draw a spade, `0xA1` a left half block, and `0xC3` the
horizontal line the support matrix already records as `0xC0`'s visual twin.

### Inverse video has no bitmap of its own

The Sinclair machines store 64 glyphs and complement them in hardware for codes
`0x80`–`0xBF`, so the inverse codes are not separately addressable. The Atom does
the same for `0x80`–`0x9F`. Only the base code is recorded.
